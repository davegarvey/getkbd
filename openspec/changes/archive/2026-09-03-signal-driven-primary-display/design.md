## Context

See `proposal.md` for the motivation and scope. The current application already
has the signals needed for this change: `DisplayMonitor` tracks the selected
external display through CoreGraphics, `USBHubMonitor` publishes a debounced
selected-hub condition, and `AppDelegate` wires both into `OwnershipController`.
The ownership state machine currently has no display-mutating dependency, which
is important to preserve.

The primary display is represented by the display at `(0,0)` in the global
display coordinate space. CoreGraphics exposes display-origin configuration as
an atomic transaction, but does not expose a separate writable primary-display
property.

## Goals / Non-Goals

**Goals:**

- Add one idempotent operation that synchronizes the primary display with the
  stable local KVM signal.
- Keep display-role changes independent of Bluetooth operation state and failure
  handling.
- Preserve the existing active display arrangement, modes, enablement, and
  mirroring state while changing only the primary role.
- Make the operation safe when the built-in display is unavailable in clamshell
  mode.
- Keep activation implicit in the existing configured display and USB-hub
  selections, without adding another persisted preference.

**Non-Goals:**

- Do not inspect, move, resize, or persist application windows. Any window
  relocation remains a macOS consequence of changing the primary display.
- Do not disable, park, mirror, unmirror, or change the mode of any display.
- Do not save and restore a complete display layout.
- Do not change keyboard ownership decisions, retry policy, or manual keyboard
  actions.
- Do not add a new settings surface, peer protocol, accessibility permission, or
  external display utility dependency.

## Decisions

### Extend the existing display adapter, not keyboard ownership

The primary-role operation belongs beside the existing display identifier and
CoreGraphics observer logic. Extend `DisplayMonitor` directly with a small
primary-role interface; do not introduce a second display service or a broader
display-state model. Keep `OwnershipController` unaware of display
configuration.

The app delegate will feed the same stable hub signal to both consumers:

```text
USBHubMonitor
      |
      +--> primary-display synchronization
      |
      +--> OwnershipController keyboard handoff
```

This avoids the failed design's coupling of display preparation and restoration
to keyboard claim/release phases. Manual keyboard actions therefore cannot
accidentally change the display role.

### Derive the target from configured KVM signals

Primary synchronization is enabled only when the selected external display and
selected USB hub are configured. While the app is awake and the selected display
is online:

- A present selected hub targets the selected external display.
- An absent selected hub targets the built-in display only when it is active.
- An absent selected hub with no active built-in display is a no-op.

The target must also be active before a configuration transaction is attempted.
This preserves clamshell behavior: the external display remains primary when the
built-in panel is closed, and opening the lid while the hub is absent makes the
built-in display eligible on the next display-activity evaluation.

### Translate origins as one app-scoped transaction

When the target is not already `CGMainDisplayID()`, read the origins of all
active displays and calculate the offset that places the target origin at
`(0,0)`. Apply that same offset to every active display in one
`CGBeginDisplayConfiguration` transaction using `CGConfigureDisplayOrigin`.

This changes the coordinate-space origin that defines the primary display while
preserving relative display placement. It does not call display mode,
enablement, or mirroring APIs. If an existing mirror configuration or an
unsupported target state prevents a safe extended-layout transaction, leave it
unchanged and report the failure.

Complete the transaction with `CGConfigureOption.forAppOnly`. This keeps the
runtime behavior local to getkbd's lifetime and avoids writing a permanent
display preference. Verify the result with `CGMainDisplayID()` before reporting
success. Do not retain a saved layout or attempt an explicit restoration on
termination.

### Synchronize only on relevant lifecycle and signal changes

Run synchronization at startup, after the debounced selected-hub condition
changes, after a selected display becomes available, after relevant active
display changes such as opening or closing the lid, and after wake. Suppress
transactions while the system is sleeping.

The display configuration notifications generated by the origin transaction
must not create a loop. Synchronization is idempotent and must use an
in-progress guard plus a post-change primary check. Ordinary layout or mode
notifications do not need to trigger a new role change; active-display
availability changes do.

### Make display configuration best-effort

A CoreGraphics transaction can fail because of transient display state,
mirroring, full-screen applications, or an unavailable target. Log a focused
display-primary failure and leave the current display configuration as macOS
left it. Continue keyboard claim or release independently, without adding a
display error to the ownership state machine for this MVP.

### Test pure decisions and validate the hardware path manually

Keep target selection and origin translation separable from CoreGraphics calls so
unit tests can cover hub-present, hub-absent, clamshell, unavailable-display,
and no-op cases without requiring attached displays. Add focused tests that
manual keyboard actions do not invoke primary synchronization if a test seam is
used.

The actual transaction and macOS window behavior require manual validation on a
two-display Mac: switch the hub signal in both directions, observe existing
windows move as macOS normally does, and repeat with the lid closed. The test
must also confirm that display modes, relative arrangement, and closed-lid use
remain intact.

## Risks / Trade-offs

- [Risk] Changing display origins can briefly rearrange the desktop or relocate
  windows. -> Accept this as the intended macOS behavior, change no modes or
  display enablement, and validate both directions manually before release.
- [Risk] macOS may reject or normalize an origin request. -> Apply one atomic
  transaction, verify `CGMainDisplayID()`, log failure, and never block keyboard
  handoff.
- [Risk] A closed laptop has no valid built-in target when the hub disappears.
  -> Require the built-in display to be active and otherwise perform no display
  operation.
- [Risk] A user may manually choose another primary display while getkbd is
  configured. -> Correct the role on the next relevant hub or lifecycle signal,
  rather than continuously fighting ordinary display notifications.
- [Risk] Application-only configuration reverts when getkbd terminates. -> Keep
  this behavior explicit and avoid permanent display changes; startup
  synchronization reapplies the role when getkbd runs again.

## Migration Plan

1. Ship the role synchronization only when the existing external display and
   USB-hub selections are configured; add no new persisted data.
2. Keep existing keyboard, display-presence, and USB-hub observers unchanged
   apart from the additional primary-role signal wiring.
3. Update the main keyboard-handoff specification and user documentation to
   replace the display-neutral contract with the hub-driven primary-role rule.
4. Rollback is code-level removal or disabling of the synchronization path. Any
   app-scoped primary change ends with the application and no permanent display
   configuration migration is required.
