## Context

See `proposal.md` for the motivation. `DisplayMonitor` currently records only
which displays are active when deciding whether a display notification matters.
macOS can change the primary display by translating the existing active displays
without changing that active set. The current wake path also clears the display
sleep gate before feeding the hub signal back into the monitor, which permits an
immediate decision from stale state.

`USBHubMonitor` already maintains a debounced selected-hub condition from IOKit
notifications. A complete IOKit enumeration can provide a fresh snapshot after
wake without changing the normal notification/debounce path.

## Goals / Non-Goals

**Goals:**

- Detect primary-display changes independently of display membership changes.
- Make wake reconciliation use a fresh hub snapshot and settle display state
  before applying a primary-role transaction.
- Preserve idempotence, clamshell no-op behavior, display arrangement, and
  keyboard/display failure independence.
- Keep the existing local-only architecture and add deterministic regression
  coverage through the display system seam.

**Non-Goals:**

- Do not persist or restore a complete display layout.
- Do not move application windows or add accessibility/window-management APIs.
- Do not change the hub-driven target policy or automatic keyboard retry policy.
- Do not continuously override ordinary user display choices when the preferred
  primary is already in effect.

## Decisions

### Track the current primary identifier

Record the primary display identifier alongside the active-display identifier set.
When a debounced display reconfiguration reports a different primary identifier,
run the existing idempotent synchronization path even if all displays remain
active. This directly covers WindowServer restoring a persistent layout after a
wake. Comparing identifiers is preferable to applying a transaction for every
display notification and preserves the existing callback loop guard.

Update the recorded identifier after a successful transaction as well as during
normal evaluation. The follow-up notification generated by getkbd's own
transaction therefore becomes a no-op rather than another configuration request.

### Treat wake release as a delayed evaluation

Keep the primary-display sleep gate set while the wake path refreshes the hub
condition. Change the wake ordering to refresh the hub, feed the resulting
stable value to `DisplayMonitor`, and only then release the gate. Releasing the
gate schedules a forced evaluation through the existing display debounce rather
than synchronizing synchronously. This lets WindowServer finish applying its
persistent display configuration before getkbd chooses a target.

The forced flag is retained across coalesced display notifications so an ordinary
notification cannot accidentally discard a required post-wake evaluation.

### Rescan USB hubs on wake

Add a synchronous `USBHubMonitor` rescan that enumerates current
`IOUSBHostDevice` services, rebuilds the hub descriptor map, and publishes one
fresh stable presence result. Normal arrival/removal notifications continue to
use their existing debounce. A rescan is used only for lifecycle recovery and
prevents a stale pre-sleep registry map from selecting the wrong primary display
or keyboard owner.

The rescan occurs while the display sleep gate is still active. If its presence
callback fires, keyboard ownership remains suppressed by its existing sleep
state; `didWake` then receives the final refreshed value and performs the normal
keyboard reconciliation.

### Preserve best-effort display handling

Keep all CoreGraphics transactions in `CoreGraphicsDisplayPrimarySystem` and do
not add display mode, enablement, mirroring, or window APIs. Include the target
and hub condition in the successful primary-display log so a future wake report
can distinguish a macOS restore from a getkbd transaction. Display failures still
only log an error and never alter keyboard ownership state.

## Risks / Trade-offs

- [Risk] WindowServer may emit several notifications while restoring displays.
  -> Coalesce them with the existing debounce, compare the primary identifier,
  and keep the primary transaction idempotent.
- [Risk] A wake-time USB enumeration may fail transiently. -> Preserve the last
  known debounced state, log the rescan failure, and allow subsequent IOKit
  notifications to recover the condition.
- [Risk] Delaying primary synchronization briefly leaves the wrong display role
  visible after wake. -> Reuse the existing 1.5-second display debounce so the
  correction occurs after topology stabilization rather than racing WindowServer.
- [Risk] A full hub rescan may produce descriptors in a different registry order.
  -> Key the map by registry ID and compare presence by the stable descriptor
  identifier; ordering is not part of the behavior contract.

## Migration Plan

1. Ship the primary-identifier tracking, wake ordering, and USB rescan together.
2. Validate hub-present, hub-absent, lid-open, clamshell, and display-only wake
   paths on hardware, including WindowServer log correlation.
3. If the wake correction is unsafe on a specific macOS release, disable only
   the post-wake primary synchronization path; ordinary hub transitions remain
   independently reversible.
